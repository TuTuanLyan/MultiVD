## Q1. DiverseVul (Chen, Ding, Alowain, Chen, Wagner; RAID 2023): what data-volume experiment was run, and the exact "may not further improve" wording

### Takeaway
DiverseVul ran two different kinds of "more data" experiments that point in different directions: (a) adding a *different* dataset (DiverseVul) on top of the merged previous datasets gave small or no gains for the best models (CodeT5 Small/Base, NatGen), which is the basis of the abstract's "may not further improve"; (b) subsampling 10%-100% of the *same-distribution* training set (100 CodeT5 Small runs) showed a monotone upward F1 trend with no clear plateau (about 38.5% to 46.2% F1, read off the plot). On unseen projects F1 stays very low (single digits to about 17%) regardless.

### Inferences
- The abstract's "may not further improve" refers to Experiment A (adding a differently collected dataset to an already large pool, with the best models at about 45-47% F1), not to Experiment B; within one distribution, the paper's own Result 7 says more data does help. Citing DiverseVul for "more data does not help" without this distinction would misrepresent it.
- Scale mismatch: the smallest subsample in Experiment B (10% of the training split) is about 0.8 x 523,956 x 0.1 = about 41,900 functions, about 3,300 vulnerable (my arithmetic from Table 3). That is roughly 90x the 456-function Python training fold; DiverseVul says nothing about the sub-1k regime.
- The Result-10 claim that CWE-502/79/89 are "well-detected" rests on 3, 12 and 9 test positives respectively (66.67% of 3 = 2 hits). As evidence that injection/deserialization CWEs are learnable from little data it is suggestive at best; the intro statement "10.5 to 48.9 F1" could not be matched to any row of Table 4 (Table 4's CVEFixes-trained best is 16.29, overall best 47.15), so prefer the Table 4 numbers when citing.

### Gaps
- Exact Figure 3 values are not printed in the text; the values above are plot readings.
- Experiment B used only CodeT5 Small and only C/C++; no learning curve on unseen projects was run.

## Q2. Steenhoek, Rahman, Jiles, Le (ICSE 2023): is there an RQ on training-set size or per-bug-type data amount, and what was found?

### Takeaway
Yes. RQ4 ("Can increasing the dataset size help improve the model performance for vulnerability detection?") trained 9 models on 1%, 5%, 10%, ..., 100% subsets of a balanced (45,363) and an imbalanced (194,285) C/C++ dataset. Gains from 10% to 100% were "not significant" (0 average F1 change on balanced; +0.16 on imbalanced), and the conclusion states models "start performing well using around 1k vulnerable examples". RQ2 compares bug-type-specific vs combined models (not a data-amount curve per type).

### Cited Findings
- **Bibliography (VERIFIED):** Benjamin Steenhoek, Md Mahbubur Rahman, Richard Jiles, Wei Le. "An Empirical Study of Deep Learning Models for Vulnerability Detection." *2023 IEEE/ACM 45th International Conference on Software Engineering (ICSE)*, pp. 2237-2248, May 2023. DOI 10.1109/ICSE48619.2023.00188. arXiv:2212.08109 (v3, 12 Feb 2023). URL read: https://arxiv.org/pdf/2212.08109 - [arXiv PDF](https://arxiv.org/pdf/2212.08109), [Crossref](https://api.crossref.org/works/10.1109/ICSE48619.2023.00188)
- **RQs as stated (VERIFIED):** "RQ4 Can increasing the dataset size help improve the model performance for vulnerability detection?" and "RQ5 How does the project composition in the training dataset affect the performance of the models?"; RQ2: "Are certain types of vulnerabilities easier to detect? Should we build models for each type of vulnerabilities or should we build one model that can detect all the vulnerabilities?" - [arXiv PDF](https://arxiv.org/pdf/2212.08109)
- **RQ4 setup (VERIFIED):** Devign + MSR (Big-Vul) combined, 82 duplicates removed, "a dataset of 194,285 examples in total"; "a Balanced-dataset of 45,363 examples by taking all the vulnerable examples in MSR and then randomly undersampling an equal number of non-vulnerable examples. For each dataset, we held out 10% data as the test set for all the models. Then we prepared 10%, 20% ... 90%, 100% of the rest of the data to train 10 models [...]. In addition, we prepared two small datasets of 1% and 5% of the total data to experiment what is the minimum amount of the data needed for the model being able to learning something." Models: Devign, ReVeal, ReGVD, CodeBERT, VulBERTa-CNN, VulBERTa-MLP, PLBART, LineVul, Code2Vec. - [arXiv PDF](https://arxiv.org/pdf/2212.08109)
- **RQ4 findings (VERIFIED):** "Generally, all the models increased in performance when we added more data. However, the improvement was not significant. Comparing 100% data with 10%, the F1 on test set reported no difference when we take an average over all the models for the Balanced dataset. For the Imbalanced dataset, the value of F1 score improved 0.16 on average." - [arXiv PDF](https://arxiv.org/pdf/2212.08109)
- **Non-monotone curves (VERIFIED):** "only LineVul showed consistent improvement when we added 10% more data each time. All other models fluctuated when we increased the training dataset, which indicates that the increasing data does not always bring benefit. For example, for VulBERTa-MLP, the F1 value drops an average 0.1 over the course of increasing the dataset sizes. The performance of the model trained with 100% of the dataset is 0.08 less than the performance of the model trained with 10% of the dataset. It seems that other factors rather than the dataset size has played a much significant role in terms of performance." Also: "ReVeal is the model that improves the most with the increased dataset. At 100% dataset, ReVeal is catching up the best model LineVul. However, Devign [...] does not show this benefit of additional data." - [arXiv PDF](https://arxiv.org/pdf/2212.08109)
- **Where the curve turns (VERIFIED):** "we can bring the models up to good performance only using 5% (about 2268 data points and 1134 vulnerable examples) for most of the models except CodeBERT, when learning with the balanced data. When learning with the imbalanced data, the turning point comes a little later. For example, ReGVD and CodeBERT require 50% (96.4 k) and 30% (57.8 k) of the total data. The other models need about 5-10% of the data (9.7-19.4 k) to reach a high point. Interestingly, this dataset has 10.8% vulnerable examples; that said, the models needed about 1048-2095 vulnerable examples to achieve good performance [...] a comparable amount of vulnerable examples to the setting of the Balanced dataset." - [arXiv PDF](https://arxiv.org/pdf/2212.08109)
- **Conclusion sentence (VERIFIED):** "The model performance does not increase significantly with an increased dataset, and for both balanced and imbalanced datasets, the models start performing well using around 1k vulnerable examples." - [arXiv PDF](https://arxiv.org/pdf/2212.08109)
- **Figure 4 (read off the plot, approximate):** Balanced (100% = 45,363): at 1% the 9 models spread from roughly 42 to 72 F1; from 10% onward most sit in roughly 60-75 F1, LineVul rising to about 79 at 100%; VulBERTa-MLP collapses to about 5 F1 at 70%; Code2Vec swings between roughly 33 and 60. Imbalanced (100% = 194,285): LineVul about 45 at 1%, about 63 at 10%, about 72 at 100%; other models mostly 25-45, ReVeal jumping to about 62 at 100%. - [arXiv PDF, p. 7](https://arxiv.org/pdf/2212.08109)
- **RQ2 per-bug-type (VERIFIED):** Five MSR groups with totals (vulnerable plus patched): buffer overflow 37,291; value error 15,126; resource error 33,748; input validation error 25,514; privilege escalation 32,749; each split 80/10/10, one model per type plus a combined model. Findings: "Input validation and Resource errors [...] often reported lower performance than the other types. On the contrary, Buffer overflows and Value errors [...] often reported better performance"; possible cause: "such errors cover a variety of resources, and the training dataset may not contain sufficient data for each resource for the model to extract the patterns." "The combined model [...] is generally less performant compared to the models trained with a specific type of vulnerability, but for some vulnerability types like Input validation and Resource errors, the combined model can perform better." "cross-bugtype detection reports much lower performance except LineVul, implying that different vulnerability types represent different data distributions." Conclusion: "Vulnerability detection based on a specific type generally performs better than a model built for all vulnerabilities." - [arXiv PDF](https://arxiv.org/pdf/2212.08109)
- **Run-to-run variability (VERIFIED, relevant background):** Conclusion: "on average, 34.9% test data have different predictions between runs, and only 7% of predictions are agreed across 9 models." - [arXiv PDF](https://arxiv.org/pdf/2212.08109)

### Inferences
- The 1% Balanced subset is 0.01 x 45,363 = about 454 examples (about 227 vulnerable), essentially the same size as one 456-function Python training fold. The paper's framing ("surprisingly, we can bring the models up to good performance only using 5%") and Figure 4a (wide 42-72 spread at 1%) place a 456-example set *below* the point where these authors saw most models stabilize, i.e., in the high-variance regime.
- The "around 1k vulnerable examples" threshold is about 4-5x the roughly 228 vulnerable functions per Python fold. It is an empirical observation on leakage-prone C/C++ data (Devign/MSR random split, 90%+ F1 range for LineVul), not a derived bound.
- RQ2 does not vary data amount within a bug type, so it cannot be cited for "per-CWE sample count vs performance"; it can be cited for "type-specific models tend to beat one combined model, and cross-type transfer is weak."

### Gaps
- Per-model numeric values for Figure 4 are not in the text (plot readings only); standard deviations across seeds for RQ4 are not reported in the text I read.

## Q3. PrimeVul (Ding et al., ICSE 2025) and other LLM-era VD studies: fine-tuning data size, per-CWE sample counts, "hard CWEs"

### Takeaway
PrimeVul runs no training-set-size or per-CWE learning-curve experiment; its data-size content is qualitative: it explicitly says manually verified datasets such as SVEN (1.6k samples, 803 vulnerable, 9 CWEs) are "not ideal for training deep neural networks" because of limited samples and diversity. Other LLM-era studies checked (To Err is Machine, Shestov et al., Jiang et al., Chan et al., Ni et al.) contain no fine-tuning-set-size curve; "To Err is Machine" reports only a pre-training-data comparison (StarCoder vs StarCoder2, "only a 4% improvement").

### Inferences
- The strongest LLM-era citation for "SVEN-scale data is small for training" is PrimeVul's own sentence about SVEN; it motivates the pre-train-elsewhere-then-fine-tune design directly, since the Python target set is a subset of SVEN.
- The only cross-dataset check found that touches SVEN (To Err is Machine: StarCoder2 7b adapter-fine-tuned on C/C++ PrimeVul, evaluated on SVEN) gave no substantial gain (worse on balanced, +1.2% on imbalanced), which is a relevant cautionary data point for transfer from a large C/C++ source to SVEN-style targets.

- "Hard CWEs have few samples" is *not* supported by the literature found; DiverseVul Table 7 is the only per-CWE evidence, and it argues the opposite (difficulty is not explained by training count).

## Q4. Does any VD paper report performance as a function of the number of vulnerable training samples, or state a minimum?

### Takeaway
No paper found states a formal minimum or a derived threshold. The closest explicit statements are empirical: Steenhoek et al. (ICSE 2023) "around 1k vulnerable examples" (about 1,048-2,095 on imbalanced data, 1,134 on balanced), and DeepDFA (Steenhoek, Gao, Le; ICSE 2024), whose Table 6 gives F1 vs (#examples, #vulnerable) from 151/11 to 150,908/8,736 and shows transformer models collapsing below about 755 examples / 56 vulnerable while a small dataflow GNN stays flat.

### Inferences
- Explicit statement for the paper: no VD study found gives a principled minimum sample count; the available numbers are empirical, C/C++-centric, and mostly on leakage-prone random splits (Big-Vul, Devign/MSR).
- The 456-example Python fold (about 228 vulnerable) sits between DeepDFA's 0.1% point (151/11, where UniXcoder fell to 4.36 F1) and its 0.5% point (755/56, where UniXcoder reached 79.37), and at Steenhoek's 1% point (about 454 examples). Both papers place this size in the steep, unstable part of the curve for transformer fine-tuning. This supports (a) reporting multi-fold, multi-seed results and (b) a transfer/pre-fine-tuning stage.
- Le et al.'s three points are confounded by language and project count, so they show association with size, not a size effect; the 0.91 C/C++ reference is a Big-Vul number and inflated.

### Gaps
- No curve found in terms of number of *vulnerable* examples for Python, or on SVEN.
- DeepDFA standard deviations are in Table 6 but were not extracted from the PDF text layer.

## Q5. Sample efficiency of fine-tuning pre-trained code models (CodeBERT, CodeT5, UniXcoder, ...) on small VD / defect datasets

### Takeaway
Direct few-shot numbers on a VD task: Wang et al. (ESEC/FSE 2022) show that on Devign with 16-128 examples per class (32-256 total), fine-tuned CodeBERT/CodeT5 reach only about 51-55% accuracy vs 62-65% with the full 21,854-example training set, and CodeT5 "does not converge" at 0 and 16 shots. DeepDFA shows UniXcoder at 4.36 F1 with 151 examples, 79.37 at 755, 95.11 at 150,908 (Big-Vul). Le et al. show CodeBERT at 0.25-0.43 F1 with 118-1,199 functions in Kotlin/Swift/Rust.

DOI 10.1145/3540250.3549113. arXiv:2207.11680 (v1). ## Q6. General ML background: small-data fine-tuning is unstable

### Takeaway
Three widely cited NLP papers document that BERT-style fine-tuning on small datasets (about 1k-10k examples) is seed-sensitive with frequent degenerate runs; Mosbach et al. (ICLR 2021) further show the instability comes mainly from too few optimization steps (which changes the LR schedule) and vanishing gradients, not from dataset size per se. These are directly useful for justifying multi-seed/multi-fold evaluation and a fixed, long-enough schedule for a 456-example fine-tuning set.

### Cited Findings
- **Mosbach et al. (VERIFIED):** Marius Mosbach, Maksym Andriushchenko, Dietrich Klakow. "On the Stability of Fine-tuning BERT: Misconceptions, Explanations, and Strong Baselines." *ICLR 2021* (PDF header "Published as a conference paper at ICLR 2021"). arXiv:2006.04884 (v3). Abstract: "fine-tuning is an unstable process: training the same model with multiple random seeds can result in a large variance of the task performance. Previous literature [...] identified two potential reasons for the observed instability: catastrophic forgetting and small size of the fine-tuning datasets. In this paper, we show that both hypotheses fail to explain the fine-tuning instability." Experiment: "we randomly sample 1,000 training samples from the CoLA, MRPC, and QNLI training datasets and fine-tune BERT using 25 different random seeds [...]. training on less data does indeed affect the fine-tuning variance, in particular, there are many more failed runs. However, when we simply train for as many iterations as on the full training dataset, we almost completely recover the original variance of the fine-tuning performance." "We conclude from this experiment, that the role of training dataset size per se is orthogonal to fine-tuning stability. What is crucial is rather the number of training iterations." "the observed increase in instability when training with smaller datasets can rather be attributed to the reduction of the number of iterations (that changes the effective learning rate schedule)". Also: "training on fewer samples affects the generalization of the model, leading to a worse development set performance on all three tasks." Guidelines "for fine-tuning transformer-based masked language models on small datasets": "Use small learning rates with bias correction to avoid vanishing gradients early in training." and "Increase the number of iterations considerably and train to (almost) zero training loss." Baseline: Adam with bias correction, lr 2e-5, 20 epochs, linear warmup over the first 10% of steps then linear decay to zero. - [arXiv PDF](https://arxiv.org/pdf/2006.04884)
- **Zhang et al. (VERIFIED):** Tianyi Zhang, Felix Wu, Arzoo Katiyar, Kilian Q. Weinberger, Yoav Artzi. "Revisiting Few-sample BERT Fine-tuning." *ICLR 2021* (PDF header). arXiv:2006.05987. "fine-tuning remains unstable, especially when using the large variant of BERT (BERTLarge) on small datasets, where pre-training stands to provide the most significant benefit. Identical learning processes with different random seeds often result in significantly different and sometimes degenerate models following fine-tuning". Causes identified: "the use of a non-standard optimizer introduces bias in the gradient estimation; the top layers of the pre-trained BERT model provide a bad initialization point for finetuning; and the use of a pre-determined, but commonly adopted number of training iterations hurts convergence." "Once these suboptimal practices are addressed, we observe that degenerate runs are eliminated and performance becomes much more stable." Few-sample regime defined via datasets "that have fewer than 10k training samples" and downsampling "all eight datasets to 1k training examples". - [arXiv PDF](https://arxiv.org/pdf/2006.05987)
- **Dodge et al. (VERIFIED; preprint):** Jesse Dodge, Gabriel Ilharco, Roy Schwartz, Ali Farhadi, Hannaneh Hajishirzi, Noah Smith. "Fine-Tuning Pretrained Language Models: Weight Initializations, Data Orders, and Early Stopping." arXiv:2002.06305 (v1, 15 Feb 2020; arXiv preprint, no peer-reviewed venue confirmed). "even with the same hyperparameter values, distinct random seeds can lead to substantially different results." "We find that both [weight initialization and training data order] contribute comparably to the variance of out-of-sample performance". "On small datasets, we observe that many fine-tuning trials diverge part of the way through training". Data: "2,100 trials". - [arXiv PDF](https://arxiv.org/pdf/2002.06305)
- **VD-specific echo (VERIFIED):** Steenhoek et al. ICSE 2023: "on average, 34.9% test data have different predictions between runs" (full-size datasets), so run-to-run variance is large in VD even before shrinking the training set. - [arXiv PDF](https://arxiv.org/pdf/2212.08109)

### Inferences
- Mosbach et al.'s mechanism (small data means few optimizer steps, which changes the effective LR schedule) is directly relevant when a 456-example fold is trained with an epoch-based linear schedule: the number of steps, not only the number of examples, should be reported and held fixed across compared arms.
- Together with Steenhoek's 34.9% prediction flip rate, these papers justify paired, per-fold, multi-seed comparisons and caution against conclusions from single runs at this data scale.

### Gaps
- None of these three papers uses code models or VD; code-model-specific stability studies at the few-hundred-example scale were not found within the search budget.
