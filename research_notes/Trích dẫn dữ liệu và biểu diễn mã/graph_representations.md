## Q1. Foundations: why graphs (CPG; Allamanis et al. program graphs; GraphCodeBERT data flow)

### Takeaway
The core argument, stated by the founding papers, is that no single linear or tree view of code carries the relations that define a vulnerability. Yamaguchi et al. merge AST + CFG + PDG because "a single representation alone is insufficient to characterize a vulnerability type". Allamanis et al. add typed semantic edges because "long-range dependencies induced by using the same variable or function in distant locations are often not considered" by token/NLP-style models. GraphCodeBERT carries the same idea into pre-training through a data-flow graph. None of these three is a learned VD model on real CVE data: CPG uses hand-written graph traversals, Allamanis et al. study VarMisuse/VarNaming, and GraphCodeBERT's paper does not evaluate VD.

### Cited Findings

**[F1] Code Property Graph (CPG). VERIFIED**
- Bib: Fabian Yamaguchi, Nico Golde, Daniel Arp, Konrad Rieck. "Modeling and Discovering Vulnerabilities with Code Property Graphs." *2014 IEEE Symposium on Security and Privacy (SP)*, May 2014, pp. 590-604. DOI 10.1109/SP.2014.44. - [Crossref record](https://api.crossref.org/works/10.1109/SP.2014.44)
- URL read (author copy, full text): https://www.mlsec.org/docs/2014-ieeesp.pdf
- Graph: one joint property graph that merges the abstract syntax tree (AST), control flow graph (CFG) and program dependence graph (PDG, i.e. data + control dependence edges); vulnerabilities are then expressed as graph traversals over it. - [CPG paper](https://www.mlsec.org/docs/2014-ieeesp.pdf)
- Reason quote (Sec. IV): "Each of the representations presented in Section II captures certain properties of the underlying software. However, a single representation alone is insufficient to characterize a vulnerability type in the vast majority of cases." - [CPG paper](https://www.mlsec.org/docs/2014-ieeesp.pdf)
- Reason quote (abstract): "This comprehensive representation enables us to elegantly model templates for common vulnerabilities with graph traversals that, for instance, can identify buffer overflows, integer overflows, format string vulnerabilities, or memory disclosures." - [CPG paper](https://www.mlsec.org/docs/2014-ieeesp.pdf)
- Numbers: identifies "18 previously unknown vulnerabilities in the source code of the Linux kernel" (abstract); the coverage study retrieved "69 identifiers addressing 88 unique vulnerabilities" from 2012 Linux-kernel CVEs, assigned to 12 types, with "47 out of 88" being memory disclosures, buffer overflows or resource leaks. - [CPG paper](https://www.mlsec.org/docs/2014-ieeesp.pdf)

**[F2] Program graphs with typed semantic edges (Allamanis et al.). VERIFIED**
- Bib: Miltiadis Allamanis, Marc Brockschmidt, Mahmoud Khademi. "Learning to Represent Programs with Graphs." *International Conference on Learning Representations (ICLR) 2018*. arXiv:1711.00740 (v3, 4 May 2018). No DOI (ICLR proceedings are on OpenReview). - [arXiv abs](https://arxiv.org/abs/1711.00740)
- URL read (full text): https://arxiv.org/pdf/1711.00740 (header: "Published as a conference paper at ICLR 2018")
- Graph: AST-based graph with syntax edges (`Child`, `NextToken`) plus data-flow edges (`LastUse`, `LastWrite`, `ComputedFrom`, as shown in Fig. 2); nodes are syntax nodes and tokens; learned with Gated Graph Neural Networks (GGNN). The paper also defines further semantic edge types not enumerated in these notes. - [arXiv PDF](https://arxiv.org/pdf/1711.00740)
- Reason quote (abstract): "most work has tried to transfer natural language methods and does not capitalize on the unique opportunities offered by code's known sematics. For example, long-range dependencies induced by using the same variable or function in distant locations are often not considered. We propose to use graphs to represent both the syntactic and semantic structure of code" (typo "sematics" is in the original). - [arXiv PDF](https://arxiv.org/pdf/1711.00740)
- Reason quote (intro): "Currently, existing deep learning models of source code capture its shallow, textual structure, e.g. as a sequence of tokens [...] Such models miss out on the opportunity to capitalize on the rich and well-defined semantics of source code." and "Our key insight is that exposing these semantics explicitly as structured input to a machine learning model lessens the requirements on amounts of training data, model capacity and training regime and allows us to solve tasks that are beyond the current state of the art." - [arXiv PDF](https://arxiv.org/pdf/1711.00740)
- Numbers: "our best model achieves 32.9% accuracy on the VAR NAMING task and 85.5% accuracy on the VAR MISUSE task" on "2.9 million lines of real-world source code" (the bug examples shown are C# projects); VarMisuse found real bugs (e.g. RavenDB, fixed in PR 4138). - [arXiv PDF](https://arxiv.org/pdf/1711.00740)

**[F3] GraphCodeBERT (data flow in pre-training). VERIFIED**
- Bib: Daya Guo, Shuo Ren, Shuai Lu, Zhangyin Feng, Duyu Tang, Shujie Liu, Long Zhou, Nan Duan, Alexey Svyatkovskiy, Shengyu Fu, Michele Tufano, Shao Kun Deng, Colin Clement, Dawn Drain, Neel Sundaresan, Jian Yin, Daxin Jiang, Ming Zhou. "GraphCodeBERT: Pre-training Code Representations with Data Flow." *ICLR 2021*. arXiv:2009.08366 (v4, 13 Sep 2021). No DOI. - [arXiv abs](https://arxiv.org/abs/2009.08366)
- URL read (full text): https://arxiv.org/pdf/2009.08366
- Graph: data-flow graph whose "nodes represent variables and edges represent the relation of 'where-the-value-comes-from' between variables"; fed to a Transformer through graph-guided masked attention, with two structure-aware pre-training tasks (edge prediction, node alignment). The data flow is extracted after parsing the code "into an abstract syntax tree (AST) by a standard compiler tool" (footnote: tree-sitter). - [arXiv PDF](https://arxiv.org/pdf/2009.08366)
- Reason quote (abstract): "existing pre-trained models regard a code snippet as a sequence of tokens, while ignoring the inherent structure of code, which provides crucial code semantics and would enhance the code understanding process." and data flow "is a semantic-level structure of code that encodes the relation of 'where-the-value-comes-from' between variables. Such a semantic-level structure is less complex and does not bring an unnecessarily deep hierarchy of AST". - [arXiv PDF](https://arxiv.org/pdf/2009.08366)
- Numbers: code-search ablation, "After ablating the data flow totally, we can see that the performance drops from 71.3% to 69.3%" (overall MRR, Table 5). The paper evaluates code search, clone detection, code translation and code refinement, not VD. - [arXiv PDF](https://arxiv.org/pdf/2009.08366)
- VD number (reported by a third paper): ReGVD states ReGVD's 63.69% accuracy on the CodeXGLUE VD set is "absolute improvements of 1.61% and 1.39% over CodeBERT and GraphCodeBERT". - [ReGVD arXiv PDF](https://arxiv.org/pdf/2110.07317)

### Inferences
- Implied by the ReGVD sentence above (arithmetic, not a number printed in GraphCodeBERT's paper): GraphCodeBERT is about 62.30% and CodeBERT about 62.08% accuracy on CodeXGLUE VD in ReGVD's table.
- For a "why graphs" sentence, [F2]'s "long-range dependencies ... in distant locations" and [F1]'s "a single representation alone is insufficient" are the two most citable primary statements. The VD-specific versions come from Devign, ReVeal and FUNDED (Q2).
- GraphCodeBERT is itself parser-dependent (tree-sitter grammar per language), which matters for the parser-free argument in Q3.

## Q2. Graph-based VD models: graph used, stated reason, headline numbers

### Takeaway
From Devign (2019) to AMPLE (2023), graph VD models share one claim: vulnerabilities depend on control/data dependencies and flows that a flat token sequence does not expose. ReVeal: "Token based models assume that tokens are linearly dependent on each other ... while the semantic dependencies are lost". FUNDED: LSTMs are "ill-suited for modeling the well-structured control and data flows of programs". Almost all of them build their graphs with Joern (C/C++). The one exception is ReGVD, which builds a token co-occurrence graph so it can stay language-independent.

### Inferences
- Across [M1]-[M9], the stated reason is always the same mechanism: vulnerability-relevant evidence is spread over statements linked by data/control dependence (use-after-free alloc/free across paths [M6]; interprocedural flow [M5], [M7]; context statements [M3]). Graph edges bring those statements next to each other; a linear token order does not. The strongest direct quotes for a paper's related-work paragraph are ReVeal's "semantic dependencies are lost" [M2], FUNDED's use-after-free sentence [M6], and Devign's "flat sequence" sentence [M1].
- Joern (C/C++) builds the graphs for Devign, LineVD, MVD and AMPLE (and for ReVeal according to AMPLE's description), and FUNDED uses one parser per language. So the "graph helps" evidence base is almost entirely C/C++ (plus FUNDED's Java/Swift/PHP).
- ReGVD [M8] shows that "graph" in VD does not have to mean "program-analysis graph": a token co-occurrence graph on top of pre-trained embeddings was competitive on CodeXGLUE (63.69%). Much of the gain there likely comes from the pre-trained embeddings rather than from semantic edges (inference; ReGVD does not isolate this).

## Q3. Language-agnostic / parser-free graphs for cross-language VD (BABEL and related)

### Takeaway
BABEL (ICSME 2024) is the clearest published argument that the parser, not the graph, is what ties graph VD to one language. Its abstract says parser-based pipelines "may cause parsing errors" and that parsers "are designed for specific programming languages", and it proposes detection "in a programming language-agnostic manner without relying on code parsers". Its released code builds two line-level graphs from shared symbolized identifiers and indentation. It is not fully language-neutral, though: its identifier symbolizer hard-codes a C/C++ keyword list, and the README recommends clang-format. ReGVD made the same "no perfect parser for each PL" argument in 2022, and FUNDED shows the alternative cost: one parser per language.

### Inferences
- DeepWukong analyses LLVM instructions through SVF, which implies its inputs must compile to LLVM IR. This is a stricter requirement than Joern's fuzzy parsing (inference from the "#LOI" statistic and the SVF pipeline; the paper does not state it as a limitation in the passages read).
- For MultiVD's cross-language setting, BABEL's argument is best cited as "parsers are language-specific and fail on real code" (abstract), with ReGVD [L2] and Devign/LineVD's parse-failure filtering [L3] as corroboration. FUNDED [M6] is the counterpoint: it reaches cross-language transfer with graphs, but pays for it with a separate parser per language.
- BABEL's "language-agnostic" claim should be stated carefully: the graph rules (shared identifier, indentation) are lexical, but the released symbolizer is C/C++-keyword-based and the indentation rule assumes formatted code, so the "no parser" claim holds while "no language-specific component" does not. The project's own reimplementation and measurements are in `FACTS.md` §67 (internal, not a publication).

## Q4. Known limitations stated by graph papers themselves

### Takeaway
The graph papers name four limitations in their own words: (1) GNNs struggle with long-range dependencies in large code graphs, and stacking layers causes over-smoothing (AMPLE, ANGLE); (2) accuracy collapses as graph size grows (AMPLE, measured on Devign); (3) heterogeneous edge types are under-used (AMPLE); (4) parser/compiler dependence drops samples and ties models to one language (Devign, LineVD, ReGVD, BABEL; Q3). Two further cautions come from graph papers themselves: ReVeal attributes much of the real-world failure to data problems rather than representation, and LineVD finds that many graph variants perform about the same as no GNN at all.

### Cited Findings
- Long-range + over-smoothing (AMPLE): "Although one can use GNNs with stacked multiple layers to learn global information (i.e., long-range dependencies among nodes) of the graph, the over-smoothing issue [24], [25] yielded from a deep GNN will lead to similar embeddings for nodes with different labels, thereby degrading the overall performance [26]." - [AMPLE arXiv PDF](https://arxiv.org/pdf/2302.04675)
- Empirical over-smoothing (AMPLE ablation): "EA-GCN with 2 layers obtains the highest accuracy of 62.16% and F1 score of 66.94%. As the number of layers continues to increase, the accuracy and F1 score decrease. We suppose that the GCN encounters an over-smoothing issue [24] with more layers". - [AMPLE arXiv PDF](https://arxiv.org/pdf/2302.04675)
- Graph size (AMPLE's motivating study of Devign): "Devign shows obviously better performance for the graphs with fewer nodes, e.g., achieving 90% accuracy for graphs with no more than 50 nodes, and drops severely as the number of nodes increases. For the graphs with more than 200 nodes, the accuracy of Devign is only around 54%." - [AMPLE arXiv PDF](https://arxiv.org/pdf/2302.04675)
- Heterogeneous edges under-used (AMPLE abstract): existing methods "do not well exploit the multiple types of edges in a code structure graph (such as edges representing data flow and control flow). Consequently, despite achieving state-of-the-art performance, the existing GNN-based methods tend to fail to capture global information (i.e., long-range dependencies among nodes) of code graphs." - [AMPLE arXiv PDF](https://arxiv.org/pdf/2302.04675)
- Large code graphs (ANGLE, PARTIAL: abstract only): Xin Peng, Shangwen Wang, Yihao Qin, Bo Lin, Liqian Chen, Xiaoguang Mao. "Keep It Simple: Towards Accurate Vulnerability Detection for Large Code Graphs." arXiv:2412.10164 (Dec 2024; venue not verified). "existing graph-based approaches mainly face two limitations that prevent them from generalizing well to large code graphs: (1) the interference of noise information in the code graph; (2) the difficulty in capturing long-distance dependencies within the graph"; reports "an improvement in accuracy of 34.27%-161.93% compared to the state-of-the-art method, AMPLE" on large graphs. - [arXiv abs](https://arxiv.org/abs/2412.10164)
- Graph gain is not uniform (LineVD): "the performance of other graph-based combinations is generally comparable to using the model without a GNN. This suggests that the program graph type and GNN type non-trivially affects the performance of the model." - [LineVD arXiv PDF](https://arxiv.org/pdf/2203.05181)
- Data, not only representation (ReVeal): existing approaches "suffer from challenges with the training data (e.g., data duplication, unrealistic distribution of vulnerable classes, etc.) and with the model choices (e.g., simple token-based models). As a result, these approaches often do not learn features related to the actual cause of the vulnerabilities. Instead, they learn unrelated artifacts from the dataset (e.g., specific variable/function names, etc.)." - [ReVeal arXiv PDF](https://arxiv.org/pdf/2009.07235)
- MVD on intraprocedural graphs: most DL approaches "take the function-level vulnerable code as input to conduct intraprocedural analysis for feature extraction, ignoring call relations between functions." - [MVD arXiv PDF](https://arxiv.org/pdf/2203.02660)
- Parser/compiler dependence: see Q3 [L1]-[L3] (Devign, LineVD, ReGVD, FUNDED, BABEL).

### Inferences
- The long-range argument cuts both ways. Allamanis et al. [F2] use graphs to shorten long-range token distances, while AMPLE/ANGLE report that inside large graphs message passing again fails over long node distances. So "graphs capture non-local relations" should be cited together with the AMPLE/ANGLE caveat.
- LineVD's "comparable to no GNN" and ReVeal's data-artifact finding both support measuring any graph component against a same-encoder, no-graph control, paired per fold. This matches how this project already compares branches.

### Gaps
- I did not find (in the papers read) a graph-VD paper that quantifies parse-failure rates across languages. Devign and LineVD only state that unparsable functions were removed; the counts were not extracted.
- Graph construction cost (time/memory of Joern) was not collected from these papers. MVD says it "makes a great trade-off between accuracy and efficiency", but the efficiency figures were not extracted.
