# Why cross-language VD transfer helps only on shared CWEs, and why C/C++ memory-safety data does not help (or hurts) a Python target

Scope note. Notes written 2026-10-05 for the MultiVD project. Every quote below was read in the full text or official page at the URL given, unless the status says PARTIAL or UNVERIFIED. Items marked "reused" were verified earlier in `research_notes/Trích dẫn dữ liệu và biểu diễn mã/` and are not re-verified here; this file re-read the full text of Risse & Böhme, PrimeVul, MVD and Chen et al. 2026 and adds new quotes from them. Status legend: VERIFIED = full text or official page read; PARTIAL = abstract or metadata only, or a table whose column alignment I had to reconstruct; UNVERIFIED = could not access. [PREPRINT] = not peer reviewed as far as I could check.

Measured pattern being explained (from the assignment, not re-measured here): SVEN Python target (760 functions; CWE-089/078/079/022); the baseline already has per-CWE ROC of about 0.98 on CWE-089 and about 0.85 on CWE-078, but 0.477 on CWE-022+079. Sources with JS (CleanVul JS, 218/495 vulnerable are CWE-079) or Java raise CWE-022+079 to 0.67-0.72. "Uncommon JS" (target CWEs removed) gives 0.31, and C/C++-only (PrimeVul) gives 0.25-0.35. Across 11 non-Java sources, Spearman(target-CWE share, macro per-CWE ROC) = +0.65 (p = 0.03). C/C++ Phase-1 on paired data reaches a validation ROC of only about 0.5 and more often leaves a degenerate model.

## Q1. Cross-language / cross-project VD papers: does transfer work mainly between shared vulnerability types or similar languages, and is there a per-CWE or language x CWE breakdown?

### Takeaway
No published VD paper I could read reports a language x CWE transfer matrix like the one measured here. The closest evidence points the same way. (a) Steenhoek et al. (ICSE 2023) find that a detector trained on one bug type transfers badly to another ("different vulnerability types represent different data distributions"). (b) Chen et al. (2026 preprint) show that after C/C++ fine-tuning, a model's "gains" on CWEs absent from its training data come from a threshold shift, not from discrimination, and that C/C++ API names act as surface triggers on Python and Java code. (c) MVD (preprint) shows that LineVul models trained on any other language reach only about 0.09-0.14 PR-AUC on Python, against 0.88 for a Python-trained model. Joint training adds almost nothing on Python, and incrementally adding C/C++ lowered Python PR-AUC. BABEL and IRC-CLVul do not publish readable per-CWE transfer results.

### Inferences
- **Explains "gain only on CWE-022+079":** [V1] is the most direct peer-reviewed VD evidence that detectors learn type-specific distributions ("cross-bugtype detection reports much lower performance"). This fits the pattern: a source helps only on the target CWEs it actually contains. CleanVul JS is 44% CWE-079 (218/495), and it is the source that lifts CWE-022+079. "Uncommon JS", the same language with the target CWEs removed, does not lift them (0.31). That isolates CWE overlap, not language similarity, as the active ingredient. This is a stronger control than anything in [V1]-[V8].
- **[V2] gives the mechanism and a warning.** Its non-overlapping-CWE "gains" were threshold shifts, which F1 counts as improvements. The project measures per-CWE ROC, which is threshold-free, so the JS/Java lift on CWE-022+079 (0.477 → 0.67-0.72) cannot be the [V2] threshold artifact. It is a real ranking change. Conversely, [V2]'s "C/C++-specific API names ... fire indiscriminately on target-language code" is a ready explanation for why C/C++ sources leave the model ranking Python functions by irrelevant cues.
- **[V3] is the only real-world, Python-target, cross-language number:** zero-shot from any other language gives Python PR-AUC of about 0.10-0.14, joint training gives about +0.005, and incrementally adding C/C++ cost about 0.017 PR-AUC. That is consistent with "C/C++ does not help Python". But [V3] also suggests that adding Java cost Python more. So in [V3], the harm comes from distribution mismatch in general, not from C/C++ specifically. MVD's Python data are CVEfixes-derived (multi-CWE), not SVEN's four web/injection CWEs, which is one reason it cannot speak to the CWE-overlap effect.
- **[V7] limits how strongly to word the claim.** Cross-cluster transfer (injection ↔ memory safety) is possible when what transfers is explicit security reasoning in a generation task. The safe wording is "for a discriminative detector fine-tuned on labelled functions, C/C++ memory-safety data did not transfer to Python web CWEs", not "memory-safety knowledge cannot transfer".
- Below-chance ROC (0.25-0.35) after C/C++ and "uncommon JS" Phase-1 means the transferred representation is anti-correlated with the label on CWE-022/079, not merely uninformative. [V2]'s indiscriminate triggers would predict a ranking near 0.5 rather than inverted. An inverted ranking needs a source cue whose sign flips in the target. See Q2 for the closest precedent (Risse & Böhme, worse-than-random accuracy on a shifted setting). That this is the specific mechanism here is a hypothesis.

## Q2. Do deep VD models learn CWE-specific / project-specific surface patterns rather than general vulnerability semantics?

### Takeaway
Yes, and several independent, mostly peer-reviewed lines of evidence agree. Risse & Böhme (USENIX Sec 2024) show that models "severely overfit to unrelated features" and fall to worse-than-random accuracy when moved to a related but shifted setting. PrimeVul (ICSE 2025) shows that code LMs rely on "textual patterns" and almost never separate a vulnerable function from its near-identical patch. That is exactly the content of paired C/C++ data, and it explains why Phase-1 on PrimeVul paired data stays at validation ROC of about 0.5. DiverseVul (RAID 2023) shows that injection-type CWEs (79, 89) are detected well even with under 2% of training data, while memory CWEs are hard despite being about half of the data. Large C/C++ corpora contain only about 2.3% of the four SVEN CWEs.

### Inferences
- **Why the baseline is already about 0.98 on CWE-089 and about 0.85 on CWE-078:** [S3] shows that injection CWEs are among the easiest to detect even with very little data. SQL/OS-command injection has a strong lexical signature (string-built queries, `execute`, `subprocess`, `os.system`). So the target already contains the surface cue, and Phase-1 has nothing to add there. This also means that per-CWE gains can only show up on the CWEs the baseline has not learned (022/079). That is what was measured.
- **Why C/C++ paired Phase-1 barely learns (val ROC about 0.5):** [S2] and [S1] show that, on vulnerable/patch pairs sharing at least 80% of their text, text-based code LMs are at or below chance. A Phase-1 run on such data has, by construction, almost no separable signal for a token model. That is the "inseparable source data" condition that the negative-transfer literature names as a cause (Q3, [T2]).
- **Why below-chance after C/C++ / uncommon-JS Phase-1:** [S1] is a peer-reviewed precedent of a model trained on one VD distribution scoring "worse than random guessing" on a related, shifted distribution. A plausible (unverified) mechanism is that the source's spurious cues ([S4], [S5]) are anti-correlated with the label in the target CWEs. For example, the patched version of a Python XSS/path-traversal function adds sanitising or escaping calls and string handling, which in C/C++ data co-occur with vulnerable code. This is a hypothesis to test (e.g., per-token attribution on CWE-022/079 test functions), not a finding.
- **Why the source CWE share predicts gain (Spearman +0.65):** if models learn CWE-specific surface patterns ([S1]-[S5]), the useful part of a source is the fraction of its vulnerable functions that carry the target CWEs' patterns. Large C/C++ corpora devote about 2.3% of training data to the four SVEN CWEs (0.47 + 0.31 + 0.38 + 1.13 in [S3] Table 7, my sum) and about 47% to CWE-119/787/125/416 (my sum). So C/C++ volume does not buy target-CWE signal.

### Gaps
- No study found reports, for Python, which surface tokens a C/C++-trained detector keys on, or measures a sign flip in attribution between source and target. The anti-correlation mechanism is unverified.
- [S3]'s per-CWE TPRs for 78/79/89/22 rest on 7-20 test positives each.

## Q3. General transfer-learning evidence that source-target similarity predicts transfer and that dissimilar sources cause negative transfer

### Takeaway
Well supported. Wang et al. (CVPR 2019) and the Zhang et al. survey (IEEE/CAA JAS 2023) name divergence between source and target joint distributions as the root of negative transfer. They also stress that negative transfer is relative to what target data alone achieves, and that inseparable or noisy source data is a separate cause. Vu et al. (EMNLP 2020) find that task and domain similarity matter most when target data are scarce, and that the largest source is not always best. Pruksachatkun et al. (ACL 2020) find that bad intermediate tasks cause negative transfer and more degenerate downstream runs. For programming languages specifically, Baltaji et al. (TMLR 2025) find that JavaScript is among the best source languages and C++ the worst, though not on a VD task.

### Cited Findings

**[T1] Wang, Dai, Póczos, Carbonell. "Characterizing and Avoiding Negative Transfer." CVPR 2019, pp. 11285-11294 (Crossref; arXiv:1811.09751). DOI 10.1109/CVPR.2019.01155. VERIFIED.**
- "2. Divergence between the joint distributions is the root to negative transfer." - [arXiv PDF](https://arxiv.org/pdf/1811.09751)
- "3. Negative transfer largely depends on the size of the labeled target data. ... On one hand, for the same algorithm and distribution divergence, NTC depends on how well the algorithm can do using target data alone". ### Inferences
- **The measured pattern is close to a textbook case of [T1]/[T2]:** the target CWE-089/078 already scores 0.98/0.85 from target data alone, so by [T1] "negative transfer is relative", and any source can only hold or lower those CWEs. The only room for positive transfer is CWE-022/079. There, the source joint distribution P(X, Y) matches the target only if the source contains those CWEs (JS: XSS-heavy). C/C++ memory-safety data diverge in both X (language, APIs) and Y-mechanism (what makes code vulnerable), which is [T2] factor 1. Paired PrimeVul data also hit [T2] factor 3 ("inseparable" source), consistent with Phase-1 val ROC of about 0.5.
- **[T3] predicts the Spearman +0.65 result in form:** with a 456-function target fold ("data-constrained"), similarity, not source size, should drive transfer. The project's similarity proxy (share of target-CWE functions in the source) correlates with gain, while the largest source (C/C++) is among the worst. [T3]'s counterpoint (dissimilar sources sometimes help) is matched by Java: CleanVul Java has no CWE labels, yet it helps CWE-022+079. One explanation is that it actually contains web/injection CWEs that are unlabelled. This is worth checking by mining CWE IDs for the Java CVEs before claiming it.
- **[T4] matches the "degenerate state" observation:** strongly negative intermediate tasks increase degenerate downstream runs. This is a peer-reviewed precedent for the observation that C/C++ Phase-1 more often leaves a degenerate model, and it ties to the project's own record of Phase-1 collapse (CLAUDE.md §7, `codebert × full`).
- **[T5] is the best code-specific analogue:** C++ is the worst source language and JavaScript an excellent one, across several tasks. It also lists Python among the worst targets, i.e. Python is hard to improve by transfer. Caveat: no VD task. It supports "language similarity matters" generally, while the project's "uncommon JS" control shows that for VD, CWE overlap matters more than language.

- No VD-specific transferability-prediction study (à la [T3]/[T5]) was found that uses CWE overlap as a predictor. The project's +0.65 Spearman appears to be new evidence, though at n = 11 sources.

## Q4. Evidence that JS/Java web-vulnerability semantics (XSS, path traversal, injection) are closer to Python web code than C/C++ memory-safety bugs are

### Takeaway
Supported by primary sources. MITRE's CWE entries tag CWE-787/125/416 as applicable to the language class "Memory-Unsafe" (C, C++). CWE-79/89/78/22 are tagged "Not Language-Specific", with CWE-79 "Web Based (Often Prevalent)". In pure Python, memory-safety CWEs therefore have no direct counterpart. Empirically, the most frequently reported CWEs in Python packages are CWE-79 and CWE-22, followed by 400, 362, 89 and 352 (PyVul, preprint). The memory-bound bugs that do appear in Python packages come largely from bundled C/C++ code. Detecting XSS in Python itself needs reasoning across server-side and client-side code, which is where JS data has vocabulary that C/C++ data lacks. C/C++ VD corpora are dominated by memory CWEs (DiverseVul Table 7).

### Inferences
- **Why JS helps CWE-079 (and CWE-022) in Python:** by [W1], XSS is a web-technology weakness whose sink is HTML/JS output. By [W2], fixing and detecting it in Python packages involves the client-side code. A JS source that is about 44% XSS teaches exactly the sink/sanitiser vocabulary (`innerHTML`, escaping, template rendering) that Python XSS functions share. C/C++ corpora contain almost none of it (0.47% CWE-79 in [W3]).
- **Why C/C++ does not help:** about half of a C/C++ corpus is memory-safety CWEs, which MITRE scopes to memory-unsafe languages [W1]. Pure-Python SVEN functions cannot contain them, so most C/C++ supervision has no counterpart in the target. The bugs it does share (injection) are a very small slice [W3]. Combined with [V2]'s C/C++ API surface triggers, this predicts null-to-negative transfer, which is what was measured.
- **Nuance for the paper:** real Python packages do contain memory bugs (9.9% of PyVul commits are out-of-bounds read/write), via C extensions [W2]. So "C/C++ data is irrelevant to Python security" is too strong. The defensible claim is "irrelevant to SVEN's four web/injection CWEs in pure-Python functions".
